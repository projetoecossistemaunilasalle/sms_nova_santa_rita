## Strategy decision

Two ways to get a migration history that matches the post-purge schema. The owner settled it on 2026-09-23; both are recorded, because the rejected one's measurements are the reason for the rejection.

### Option A — dossier §6.3 as written, which is also the plan as written (**chosen**)

Leave `0_init` … `5_v1_game_events` exactly where they are and add one directory, `prisma/migrations/6_drop_generation_a/migration.sql`. `REFACTOR_PLAN.md:86` asks for that file by name — "6. Generate and track `prisma/migrations/6_drop_generation_a/migration.sql`" — so **this phase contains no deviation from `REFACTOR_PLAN.md`**, and the deviation previously booked against §2.5.6 is withdrawn. `COMPAT-POLICY.md` §2 row 1 classed the history **A** and §4.1 recommended collapsing it into a regenerated init; §6 row 1 **rejects the recommendation while accepting the classification**. Those are separate questions: "this is internal-legacy, so we are *allowed* to drop it" does not license dropping it when the alternative measures more expensive.

What Option A no longer carries is the verification machinery built around it. `COMPAT-POLICY.md` §4 edits 2-3 deleted that machinery and §6 **adopted** the deletion, so these are struck from this phase and from Phase 4's `ci.yml`:

- the drift gate `npx prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --exit-code` (`REFACTOR-DOSSIER.md:308-309`);
- the Postgres `services:` container and `SHADOW_DATABASE_URL` (`:511`);
- the two `prisma.config.ts` datasource keys §6.5 made a prerequisite (`:296-303`) — the file today defines `schema`, `migrations.path` and a conditional `datasource.url` fed from `DIRECT_URL` (`prisma.config.ts:6-11`), and no `shadowDatabaseUrl`;
- the throwaway-`DIRECT_URL` `migrate deploy` runbook (`:290-294`), already out of scope per `COMPAT-POLICY.md:26`.

**The consequence, stated flatly: this refactor ships with no schema-drift gate at all.** `COMPAT-POLICY.md:69` says so in terms — the DB-free byte-compare that edit 2 offered as a substitute is "**only available if edit 1 is adopted**", and edit 1 was not. With a sequential history, "do these migrations reproduce `schema.prisma`?" can only be answered by replaying them, and `migrate diff --from-migrations` has no `--script`-only path around a shadow database. **No cheaper gate replaces the old one; the old one is simply gone.** What remains is `prisma validate`, which checks the schema against itself and never opens `prisma/migrations/`. The honest offset is that the deleted leg never worked: `phases/00-prerequisites.md` §4 0.3 ran it and got exit **1**, "You must set `datasource.shadowDatabaseUrl` in your `prisma.config.ts` if you want to diff a migrations directory" (quoted at `COMPAT-POLICY.md:70`). The ruling removes a non-functional step, not a running check — but the check this phase *needs*, on the file this phase *adds*, is now covered by nothing outside this document.

**Cost.** One hand-written SQL file — 8 statements as transcribed at `REFACTOR-DOSSIER.md:257-274` and `ADJ-01:34-51`, and **10** once `AuditEvent` is dropped with the rest of the purge (step 8's reconciliation finding, plus why the two additions are a table *and* its constraint) — plus 386 lines of history carried forward. The history is not decoration, and it is not what §6.3 called an "audit trail of what shipped when": `prisma/migrations/1_add_paused_at/migration.sql` is 3 lines whose only statement `ALTER`s `access_links`, a table this same purge `DROP TABLE`s (`REFACTOR-DOSSIER.md:269`) — that self-cancellation is exactly why §6 strikes the audit-trail framing. Its real residual value is different, and no document in the decision chain named it: `prisma/migrations/2_v1_adult_roles_and_classes/migration.sql:13-27` and `:32-41` are two `UPDATE … FROM "capability_assignments"` statements that backfill `professional_profiles.platform_role` and rewrite every `organization_memberships.role` from the legacy grants. They transform **rows**, not schema, so a regenerated-from-empty init cannot contain them; collapsing the history would have deleted the only record of how Generation-A capability grants became Generation-B roles.

**Risk.** Medium, front-loaded, and **now unpoliced by any tool**: a hand-authored DROP sequence is precisely the artifact that goes stale silently, and §6.5's own words — "The CI gate is therefore a prerequisite, not a one-liner" (`:312`) — describe the thing that has just been deleted. The controls that remain are manual, so this phase makes them explicit: step 7's object inventory, step 8's regeneration command (the file is *emitted* by the tool and compared against the dossier's transcription, not typed from memory), and the line-by-line read `ADJ-01:66` already argued is "the correct control" at this size.

### Option B — purge and regenerate (**rejected by the owner, 2026-09-23**)

The shape was: delete the six unapplied directories, generate one cumulative `0_init` from the post-purge schema, and carry the objects Prisma cannot express in one hand-written `1_datamodel_extras`.

```bash
npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script > prisma/migrations/0_init/migration.sql
```

**This section is the justification for the rejection, not work to do. Nothing in it is executed by this phase.** Five facts, re-confirmed against the tree at `e5aaf1e`, are why the cheaper-looking option was refused:

1. **The saving is roughly half what the recommendation priced it at.** `COMPAT-POLICY.md:24` says "~410 SQL ln → ~190". The "~410" is right (386 tracked + 23 for the hand-authored sixth). The output side is not: the command was run for the earlier revision of this file against a scratch post-purge copy and produced **269 lines**, so the true end state was ~410 → ~290 — **~120 lines saved, not ~220**, i.e. `:24` understated the output by ~100. `COMPAT-POLICY.md` §6 row 1 re-measures it identically.
2. **16 invariants would have had to be hand-appended to that generated file:** 8 `CHECK` constraints, 2 partial unique indexes, 6 `gen_random_uuid()` defaults. Miss one and the init silently weakens the database with every gate green. The list, verified line-by-line against the tree rather than copied from `COMPAT-POLICY.md:24`:
   - **8 surviving `CHECK` constraints** — 1 in `3_slice_02_player_access:15` (`player_slots_player_number_positive`), 3 in `4_v1_game_state:12-14` (`game_states_revision_check`, `game_states_protocol_version_check`, `game_states_schema_version_check`), 4 in `5_v1_game_events:18,20,43,45` (`duration_ms >= 0`, the `result_state` value set in Portuguese, `active_ms BETWEEN 1 AND 30000`, the `mode` value set). The other 5 are `0_init:163,166,169` on **`access_links`** and `0_init:172,175` on **`rate_limit_buckets`** — both dropped, so they die with their tables. Measured, not assumed: `grep -rc CHECK prisma/migrations/*/migration.sql` → `0_init` 5, `1_…` 0, `2_…` 0, `3_…` 1, `4_…` 3, `5_…` 4 = **13 total, 8 surviving**. `COMPAT-POLICY.md:107` re-counts it the same way.
   - **2 partial unique indexes** — `3_slice_02_player_access:56` `player_credentials_one_active_per_slot … WHERE "status" = 'active'` and `:58` `game_sessions_one_active_per_class … WHERE "status" = 'active'`, both verbatim in the tree (`grep -rn "UNIQUE INDEX.*WHERE"` → exactly these 2).
   - **6 `gen_random_uuid()` defaults** on surviving tables — `2:47` (`class_groups.id`), `2:60` (`teacher_assignments.id`), `3:8` (`player_slots.id`), `3:20` (`player_credentials.id`), `3:31` (`game_sessions.id`), `3:43` (`participations.id`), each the `"id" UUID NOT NULL DEFAULT gen_random_uuid(),` line immediately below its `CREATE TABLE`. `grep -rn gen_random_uuid prisma/migrations/*/migration.sql` → exactly 6 hits, at those lines.
   Also in the same family, the one that does **not** survive: `capability_assignments`' `NULLS NOT DISTINCT` raw unique index at `0_init:160`, documented as un-Prisma-able at `schema.prisma:254-256` — it goes with the table either way, and under Option A the `DROP TABLE` takes it without anyone having to remember it.
3. **`schema.prisma` expresses none of them, so no automated check could have noticed.** `grep -rn dbgenerated prisma` → **0 hits** (re-run here; `grep -c dbgenerated prisma/schema.prisma` → `0`). The schema is silent on all 16 objects.
4. **Nothing in the suite covers it:** no test executes SQL and no test asserts on `prisma/migrations/**` (see *Tests*), so the suite cannot catch a wrong append either.
5. **The byte-compare substitute is blind to the extras by construction — and is unavailable anyway** (`COMPAT-POLICY.md:69`). Measured on this schema the generator emits **0 `CHECK`**, **0 `gen_random_uuid`**, no `WHERE`-qualified index and no `NULLS NOT DISTINCT`: it re-derives only what the schema can express, which is precisely none of the 16.

**The sharpest instance, found by doing the rejected run anyway.** `@default(uuid())` is client-side in Prisma 7, so a regenerated init emits `"id" UUID NOT NULL` with **no `DEFAULT` clause at all**. Eleven of the twelve surviving models carry a `@default(uuid())` id — `grep -cE '@id @default\(uuid\(\)\)' prisma/schema.prisma` → **14** at HEAD, less the three purged UUID-keyed models at `:246`, `:262`, `:282` = **11**; `RateLimitBucket`'s key is `@db.Char(64)` (`:301`) and `GameState`'s is a FK (`:183`), so neither is in the count. Prisma-Client inserts keep working; raw SQL — the hand-inserted `professional_profiles` row §6.6 says `AUTH_DEV_BYPASS` needs, a seed script, a repair query — fails with `null value in column "id" violates not-null constraint`. `REFACTOR-DOSSIER.md:314` argued this as a later `ALTER COLUMN … DROP DEFAULT`; the true shape is at once worse and narrower — immediate, silent, and raw-SQL-only.
   **And one correction in Option B's favour, because it changes what the extras were actually worth:** the current history supplies a server-side default for only **6 of those 11** (`2:47,60`, `3:8,20,31,43`). The other five — `professional_profiles`, `organizations`, `organization_memberships`, `result_events`, `active_time_events`, at `0_init:12,24,36` and `5:2,31` — have **never** had one, and no migration anywhere adds or removes one: `grep -rn "SET DEFAULT\|DROP DEFAULT" prisma/migrations/*/migration.sql` → **no output**. So `1_datamodel_extras` would have *restored parity across 6*, not preserved an invariant across 11, and the raw-SQL path is already broken today on `professional_profiles` — the exact table §6.6 names. That softens objection 2 without reversing it: six silently-lost UUID defaults plus eight silently-lost `CHECK`s is still past the threshold, and §6's ruling stands on the whole list.

**Rejected** at `COMPAT-POLICY.md:67` and §6 row 1 (owner, 2026-09-23). The §2 row's **A** classification stands; only its adoption is withdrawn. `COMPAT-POLICY.md:88` (§5.5 — the earlier revision of this file cited it as `:84`, which is §5.1) asked "whether `migrate diff --from-empty --to-schema` emits exactly the intended init". That run *was* performed for this file and is recorded below, and §6 declares it **moot**: no cumulative init is generated, so nothing has to be emitted correctly.
